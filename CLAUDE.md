# lazyset

Lightweight Python library for reading/writing databases as easily as JSON — a thin layer over SQLAlchemy, no ORM models. Supports SQLite (default), PostgreSQL, MySQL. **Design bias: simplicity over features — don't over-engineer.**

**Hard fork of [pudo/dataset](https://github.com/pudo/dataset).** The import name is `lazyset` (first release 0.1.0). **Not published to PyPI** — the name is too close to an existing project there — so the only distribution channel is git: `pip install git+https://github.com/medecau/lazyset@vX.Y.Z`. Keep that in mind for anything that assumes a registry (version pinning, install docs, release automation). This fork deliberately breaks from upstream: four self-describing write verbs (`insert`/`upsert`/`update`/`delete`, each taking one row **or** any iterable of rows), one honestly-named `auto_create` flag, and loud errors where 2.x was silently wrong. There are no upstream users of the fork to shepherd — see the fork-line policy under Must-follow.

## Layout
- `lazyset/database.py` — `Database`: connection, transactions, `query()`, `db[name]` / `db.table(...)` accessors
- `lazyset/table.py` — `Table`: CRUD, schema management, filter operators (`_generate_clause`)
- `lazyset/types.py` — type mapping (`Types.guess`), `ColumnType`
- `lazyset/util.py` — `Results`, name normalization, exceptions, type aliases
- `test/` — pytest; `conftest.py` = `db` + `table` fixtures, `sample_data.py` = shared test data, `test_properties.py` = Hypothesis tests for pure helpers, `test_docs.py` = runs the examples in `README.md` and `docs/*.md`

## Commands
- Deps/env: `uv` (`uv run`, `uv sync`). Run tests: `make test` (or `uv run pytest`).
- **Deps are split two ways.** `[dependency-groups] dev` (PEP 735) holds the tooling — pytest, hypothesis, ruff, ty, pdoc, mutmut, tox — plus the backend drivers, because CI tests all three backends. `uv sync` installs it by default; CI says `uv sync --group dev` explicitly. `[project.optional-dependencies]` holds only the two *user-facing* extras, `postgresql` (psycopg2-binary) and `mysql` (`PyMySQL[rsa]` — the `rsa` extra brings cryptography for MySQL 8's caching_sha2_password). Don't put tooling in an extra: extras are part of the installable surface, groups are not. Don't write the drivers into the dev group as a self-reference (`lazyset[mysql,postgresql]`) either — only uv resolves that to the local project; every other installer goes to PyPI, where `lazyset` is someone else's package.
- `make check` — ruff format `--check`, ruff lint, and `ty check` over the whole repo (`lazyset/` **and** `test/`). Run before committing; `make test` depends on it.
- `make fix` — apply ruff format + `ruff check --fix`. Test another backend with `DATABASE_URL=postgresql://… make test`.
- Mutation testing: `uv run mutmut run` then `uv run mutmut results` (dev dep). Current baseline on SQLite under mutmut 3.6: **1319 mutants, 885 killed, 422 survived, 12 skipped** — diff against that rather than re-triaging from scratch. The survivor *categories* in `CHANGELOG.md` under 2.0.0 (dialect-guarded paths, equivalent mutants) still apply, but its counts predate mutmut 3.x and are not comparable.

## Must-follow
- **Keep docs current:** when you change code, commands, deps, or public API, update the docs the change touches in the same pass — this `CLAUDE.md`, `README.md`, the docstrings, `docs/*.md`, `CHANGELOG.md`. A stale doc is a bug.
- **Multi-backend:** every change must work on SQLite, PostgreSQL, AND MySQL. Branch on `db.is_sqlite` / `is_postgres` / `is_mysql`. MySQL text indexes need a prefix length (10 chars). `drop_column` is attempted on every backend and the DB decides (SQLite ≥ 3.35 supports it; older SQLite raises).
- **Sane single-row rowcount is assumed:** `update()`/`delete()` return `rp.rowcount` directly, with no COUNT fallback — lazyset requires a dialect where `supports_sane_rowcount` holds (SQLite, PostgreSQL and MySQL all do). The *multi*-row fallback in `_flush_update_chunk` stays: `supports_sane_multi_rowcount` is genuinely False on psycopg2.
- **Fork-line — breaking changes are sanctioned:** this is a hard fork with no upstream users to shepherd, so renaming/removing public API is allowed when it makes the surface clearer. The redesign does exactly that: `ensure`→`auto_create`; `insert_many`/`update_many`/`upsert_many` folded into `insert`/`update`/`upsert` (`Mapping` **or** `Iterable[Mapping]`, dispatched by shape); `chunked.py` deleted in favour of `insert(gen, chunk_size=N)`; accessors collapsed to `db[name]` / `db.table(...)`; `ResultIter`→`Results`, `OutRow`→`Row`. Rules that still bind: rename deliberately, land the change with its doc + test sweep in the **same pass**, and record every break in `CHANGELOG.md`. `create_column`'s `type` param shadows the builtin — keep it (ruff's A002 is not enabled, so no `# noqa` is needed); a cosmetic rename buys nothing.
- **One statement choke point:** every statement goes through `db._execute(stmt, params, conn=None)`, which rolls the connection back on error outside an explicit transaction. Never call `connection.execute` directly; pass `conn=` for the streamed connection `find(_streamed=True)` opens.
- **Auto-commit:** call `db._auto_commit()` after any write made outside an explicit transaction — including a write issued through `db.query()` (gate on `rp.returns_rows`).
- **Thread safety:** hold `self.db.lock` for schema ops; connections are thread-local; transaction depth lives in `self.local.tx`.
- **Don't mutate input rows:** copy to `dict()` before modifying (see `update`, `insert` iterable paths).
- **Delegate to SQLAlchemy and the database.** Prefer built-in SQLAlchemy behavior and database-enforced semantics over re-implementing them in Python:
  - Let SQLAlchemy bind and render values (bind parameters, type coercion, identifier quoting, dialect literal rendering) — never hand-roll SQL-value serialization.
  - Let the database decide row existence, equality, collation, NULL semantics, server-side defaults, and identifier limits — don't classify/compare in Python where SQL semantics (NULL, type affinity, case-insensitive collation) would differ.
  - A "performance" rewrite that moves such a decision into Python must clear correctness-vs-the-DB as its acceptance bar. Reintroducing a hand-rolled version of what the stack already does correctly is a bug, not an optimization.
- **Version:** bump with `bump2version`, never edit `lazyset/__init__.py` directly.

## Conventions
- **Types:** the type checker is **ty** (Astral), not mypy; `lazyset/` ships `py.typed` and `test/` is checked too. `ty` infers the target version from `requires-python`, so it checks against the 3.10 floor — no `[tool.ty]` config is needed. Use `WriteRow` (`Mapping`) at public boundaries, `MutableRow` (`dict`) internally where mutation happens — copy only at that boundary. `ColumnType` for `primary_type` / `create_column`.
- **Suppressions:** ty ignores `# type: ignore[mypy-code]` — a mypy error code is not a ty rule name, so those comments are silently inert. In `lazyset/` use `# ty: ignore[<rule-name>]` with the rule ty actually reports, plus a line saying what the type system cannot see. In `test/` prefer a bare `# type: ignore`, which ty *and* an editor's pyright both honour, for the deliberately-wrong-type calls and monkeypatched methods that tests need.
- **Shape dispatch:** `isinstance(rows, Mapping)` does not prove `WriteRow` — a `Mapping` is also an `Iterable` (of its keys), so a row-keyed mapping inhabits both arms of `WriteRow | Iterable[WriteRow]`. The single-row branches go through `_as_row()`, which states that reading once instead of at every verb.
- **Columns:** match case-insensitively via `_get_column_name()`; `_column_keys` preserves the real DB names.
- **Errors:** `DatasetError` is the base, `QueryError` for invalid filters; name exception classes with an `Error` suffix.
- **Python 3.10+:** `X | None`, builtin generics (`list[str]`, `dict[...]`).

## Transactions (SQLAlchemy 2.x)
2.x "autobegin" starts a transaction on first use; `_auto_commit()` commits after writes when no explicit transaction is open. Nested and non-nested transactions must both work — test both, and with multiple threads. See `begin()` / `commit()` / `rollback()` in `database.py`.

## Docs & scope
API reference is generated from docstrings with **pdoc** (`make docs` → `site/`) and published to **GitHub Pages** by CI (`ci.yml`: the `docs` job builds and uploads the artifact on every push/PR, `deploy-docs` publishes it on `main` only). Pages is enabled on the repo with `build_type=workflow`; the workflow cannot self-enable it, because `actions/configure-pages`' `enablement` input requires a PAT rather than the job's `GITHUB_TOKEN`. `__all__` in `lazyset/__init__.py` is what pdoc renders, so the whole public surface lands on one page and there are no submodule pages. The two narrative guides live as `docs/quickstart.md` / `docs/queries.md` and are pulled into the `lazyset` landing page via pdoc's `.. include::` in `lazyset/__init__.py` (paths resolve against the source checkout, not the wheel). Docstring cross-refs are bare backtick identifiers (`` `Table.find` ``), not Sphinx roles. **The guides are executed.** `test/test_docs.py` runs `README.md` and `docs/*.md` top to bottom as one session each: ```python fences are `exec`'d, ```pycon transcripts go through the stdlib `doctest` module, and both share one namespace, so a guide is tested the way a reader reads it. Consequences when editing a guide: it has to work as a continuous session — a block that rebinds or closes `db` poisons everything below it unless marked. Two HTML comments (invisible when rendered) go *above* a fence — blank lines in between are tolerated, because Markdown formatters insert them around an HTML block: `<!-- example: skip -->` for a block that cannot run (placeholder metasyntax, another backend's driver, a table the guide never creates — still syntax-checked), `<!-- example: isolated -->` for a side example that runs against a copy of the namespace. A marker that binds to no fence fails the test rather than silently reverting the block to a session step. Transcripts always get a copy, so a ```pycon block reads the session but never writes to it. Write verifiable output under a ```pycon fence with `>>>`, never a bare ```python block with the output pasted in — ruff formats the latter as source and rewrites the *output* (`['user']` → `["user"]`, which Python never prints). `addopts = "--doctest-modules"` covers `>>>` in docstrings on top of that. Changelog in `CHANGELOG.md`. Release: `bump2version` → update `CHANGELOG.md` → push a signed tag `vX.Y.Z`. The tag push runs `cd.yml`, which re-tests on SQLite, builds the sdist/wheel, smoke-tests `pip install git+…` against that commit, and cuts a GitHub Release with the artifacts attached. There is **no PyPI step**: the tag itself is the release, and that is what users pin in `pip install git+…@vX.Y.Z`, so tags are immutable once pushed.
Out of scope: FK/relations, Python-side JOINs, async. DB-native UPSERT is the single `upsert()` algorithm (`ON CONFLICT DO UPDATE` / `ON DUPLICATE KEY UPDATE`); key-only rows degrade to `DO NOTHING` / ODKU-noop, which is why there is no separate `insert_ignore()`. `upsert()` requires `keys` as the conflict arbiter and creates the UNIQUE arbiter index under `auto_create`.
